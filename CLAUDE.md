# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

**SG Buddy** — локальная GUI-программа на NiceGUI. Читает DDL-схему Postgres, даёт
настроить запросы и связи по каждой таблице и пишет настройки в `schema.json`.
Из этих настроек генерируются `query.sql` для sqlc и `*.proto` для gRPC.

Каталог репозитория называется `grpc_sqlc_gui_helper` (историческое имя), пакет —
`sgbuddy`, команда — `sgbuddy`.

## Команды

```bash
uv run sgbuddy                      # http://127.0.0.1:8080
uv run sgbuddy --native             # отдельным окном
uv run sgbuddy --no-show --port N   # без открытия браузера, для проверок
uv run pytest                       # 248 тестов: ddl, settings, оба генератора, формы
```

Проверка «поднимается ли»: запустить с `--no-show` на свободном порту, дёрнуть
`curl` и погасить процесс — сервер сам не завершается.

Версия задаётся в `pyproject.toml` и только там: `release.yml` выпускает по ней
релиз `v<версия>` при push в `main`, если такого ещё нет. Поднимать номер —
значит выпускать; что в какой версии появилось, пишется в `CHANGELOG.md`.

Вместе с номером обновляется `uv.lock` (`uv lock` или любой `uv run`): версия
самого проекта записана и там, а `tests.yml` ставит окружение с `--locked` и
роняет прогон, когда файлы разошлись. Отставший lock не даст выпустить релиз —
тесты в него входят условием.

## Архитектура

Поток данных линейный: `schema.sql` → `ddl.py` → модели в памяти → формы в
`app.py` → словарь настроек → `settings.py` → `schema.json`.

| Файл | Ответственность |
|---|---|
| `sgbuddy/ddl.py` | **Единственное место, знающее синтаксис SQL.** Разбор `CREATE TABLE` через sqlglot в `Table`/`Column`. Правился только аддитивно. |
| `sgbuddy/settings.py` | Формат `schema.json`: ключи-константы, чтение/запись, навигация по разделам `CRUD` (`entries_of`, `ensure_directions`) и `JOINS` (`joins_of`, `ensure_joins`, `join_by_name`), миграция старого формата. Ключи задаются здесь и только здесь. |
| `sgbuddy/query_gen.py` | Перевод настроек в `query.sql` для sqlc. Все правила перевода — в docstring модуля. Файл кладётся в папку схемы, рядом со `schema.json`; своего ключа с путём в настройках нет. Здесь же разбор цепочек join'ов (`read_joins`, `read_fields`) — им пользуются оба генератора. |
| `sgbuddy/proto_gen.py` | Перевод тех же настроек в `*.proto`. Поля запроса читаются из **готового SQL**, который отдаёт `query_gen`: контракт описывает то, что действительно уйдёт в базу. Путь к файлу спрашивает мастер и хранит ключ `save_proto_path`. |
| `sgbuddy/app.py` | Весь интерфейс: стили, мастер из трёх шагов, сайдбар таблиц и пять форм (Create/Read/Update/Delete/Join). |
| `sgbuddy/__main__.py` | Разбор аргументов и `ui.run`. |

### Состояние

Программа локальная и однопользовательская, поэтому состояние — модульные
синглтоны в `app.py`: `workspace` (выбранные пути, разобранные таблицы,
загруженные настройки) и пять черновиков форм `form`, `read_form`,
`update_form`, `delete_form`, `join_form`. Черновик живёт до нажатия «Добавить» и сбрасывается,
когда меняется таблица.

Вся перерисовка идёт через один `@ui.refreshable def wizard()`. Любая функция,
меняющая состояние, заканчивается `wizard.refresh()`. Обработчики `on_change` у
полей ввода этого **не делают** — иначе форма перерисовывалась бы на каждый
символ и теряла фокус. Перерисовка при вводе допустима только там, где от
значения зависит состав формы: аннотация `many` в Read, режим в Delete,
включённая цепочка join'ов (от неё зависят сетки колонок), выбор таблицы в звене
(подставляет алиас) и добавление или удаление звена.

`workspace.reset()` обходит поля через `dataclasses.fields`, чтобы новое поле
сбрасывалось само; `reset_all()` дополнительно обнуляет все пять черновиков.

Правка и копия записи — **один и тот же перенос в форму**: `_edit_*(index,
table, editing=False)`, он же `_copy_*`. Разница одна — у копии `editing`
остаётся пустым, и сохранение заводит новую запись рядом, а не переписывает
исходную. Название копируется как есть: имена уникальны (запросы — по файлу,
цепочки — в пределах таблицы), и переименовать копию должен автор.

## Формат `schema.json`

Лежит рядом со `schema.sql`. Чистый JSON: пояснение «что это за файл» —
первым ключом `description`, комментариев в файле нет. Читать всё равно через
`settings.load_settings`: файлы прежнего формата начинались со строк `//`
(JSONC), и `_strip_header` их снимает.

```
{
  "description": "...",          // подпись программы, перезаписывается при каждом сохранении
  "schema_folder_path": "...",   // эти пять ключей всегда первые и в этом порядке:
  "save_proto_path": "...",      // всё, что мастер спрашивает до разбора схемы
  "proto_package": "...",        // package в .proto; пустой — строки в файле не будет
  "go_package": "...",           // option go_package; через windows_path не проходит
  "CRUD": {
    "dc.alias": {                // таблица целиком, с именем схемы
      "CREATE": [ { "Name": ..., "Query Annotation": ..., "columns": [...], "custom_query": ... } ],
      "READ": [], "UPDATE": [], "DELETE": []
    }
  },
  "JOINS": {
    "dc.column_cat": [           // цепочки таблицы, каждая под своим именем
      { "Name": "with_table",
        "joins": [ { "type": "INNER", "table": "dc.table_cat", "alias": "t",
                     "on": "t.id = column_cat.table_id" } ] }
    ]
  }
}
```

Цепочка описывает связь таблицы, а не запрос, поэтому лежит рядом с `CRUD`, а не
внутри него: одну и ту же цепочку включают в себя несколько выборок. Звеньев в
ней столько, сколько таблиц присоединяется по порядку, — связь «многие ко
многим» это два звена: связующая таблица и целевая.

Выборка, которая цепочки использует, получает два ключа сверх обычных:
`joins` — имена включённых цепочек, и `joined_columns` — колонки приджойненных
таблиц теми же флагами, что `columns`, плюс `join` и `alias`. Отдельным списком,
а не внутри `columns`: там `column_name` читается как колонка своей таблицы, и
`id` базовой перестал бы отличаться от `id` приджойненной.

Набор ключей внутри `columns` **разный у направлений**: у CREATE это
`column_value`, у READ — `show`/`where`/`where_optional`/`exact_where`, а при
аннотации `many` ещё `order_by`/`order_by_optional` (у `one` строка одна, и
порядок ей ни к чему),
у UPDATE — `set`/`set_value`/`where`/`where_optional`/`where_value`,
у DELETE — то же, но `set`/`set_value` пишутся только в режимах `SOFT DELETE`
и `UNDELETE` (оба дают `UPDATE ... SET`, а `DELETE` — физическое удаление).

Правила, которые легко нарушить незаметно:

- **Незаполненное текстовое поле пишется как `null`**, не как `""`. Исключение —
  `column_value` в CREATE: там пустое поле означает «приходит параметром» и даёт
  `@имя_колонки`.
- **Имена запросов уникальны по всему файлу** (`_name_taken`), а не в пределах
  таблицы: sqlc не разрешит двойника нигде.
- **Разделы таблиц заводятся лениво** (`ensure_directions` только при записи,
  `entries_of`/`directions_of` при чтении). Иначе от простого просмотра в файл
  упали бы пустые блоки всех шестнадцати таблиц.
- **Старый плоский формат** (`CRUD -> CREATE -> [{Table: ...}]`) встречается на
  дисках. `migrate_crud` разносит его по таблицам при чтении — не убирать.
- **Алиас звена — простое имя латиницей и не слово SQL** (`is_alias` в
  `query_gen`). Из него собираются имя колонки на выходе (`t_name`) и имя её
  параметра (`@t_name`), а `@"my alias_id"` не бывает.
- **Ключи `joins` и `joined_columns` пишутся только тем выборкам, которые
  join'ы используют.** У остальных запись остаётся ровно такой, какой была до
  появления раздела.
- **Имя цепочки уникально в пределах таблицы** (в sqlc оно не попадает), а
  переименование и удаление цепочки ведут за собой ссылки в `READ`
  (`_rename_join`, `_forget_join`): выборка со ссылкой на исчезнувшую цепочку
  не соберётся вовсе.
- Сгенерированные файлы (`.proto`, JSON) **затираются целиком без подтверждений**.
  Диалогов «файл существует» быть не должно; в интерфейсе про это сообщают
  фактом, а не предупреждением.

## Генерация

`render()` возвращает текст и список `Problem`. Запрос, который нельзя собрать
(нет колонок, `UPDATE` без изменяемых колонок, ссылка на несуществующую колонку),
**пропускается с объяснением**, а не роняет генерацию целиком; опасные, но
осмысленные случаи (удаление без `WHERE`) помечаются `fatal=False` и всё равно
попадают в файл. Интерфейс показывает эти строки под сводкой.

`RETURNING *` всегда идёт последним: `custom_query` существует ради
`ON CONFLICT ...`, а он в Postgres пишется до `RETURNING`.

Выборка с join'ом **обязана перечислить колонки**: `SELECT *` вернул бы столбцы
всех соединённых таблиц вперемешку и с повторяющимися именами, а такой файл sqlc
не примет, — запрос без единой отмеченной колонки пропускается. Колонки
приджойненных таблиц выходят под именем с алиасом (`t.name AS t_name`), и это же
имя носят их параметр и поле в `.proto`; в контракте они объявляются `optional`,
когда соединение вправе не дать строки (`LEFT`, `FULL`). Разбирает цепочки
`query_gen.read_joins` — оба генератора зовут её, чтобы видеть одни и те же
звенья.

**Двух одинаковых имён в `SELECT` не бывает.** Совпасть они могут и после
алиаса: у `dc.column_cat` есть своя колонка `alias_id`, и звено с алиасом
`alias` даёт `alias.id AS alias_id`. Имена раздаёт `read_fields` (`_unique_out`),
второму вхождению приписывается номер — `alias_id_2`, — и под ним же колонка
уходит в файл через `AS`. Это имя носят её параметр (`@alias_id_2`), выбор
сортировки и поле в `.proto`: имя решается в одном месте, поэтому SQL и
контракт называют колонку одинаково.

**Колонка, допускающая `NULL`, даёт `optional`-поле** — в сообщении таблицы, в
своём `<Имя>Row` и в параметрах вызова. Исключений по типу нет: nullable дата
объявляется `optional google.protobuf.Timestamp`, хотя присутствие у сообщения
различимо и без него, — иначе `NULL` колонки в контракте не виден глазами.
`optional` получают ещё необязательный фильтр (`sqlc.narg`) и колонки стороны,
которую соединение вправе оставить пустой.

**Первичный ключ обязателен всегда**: `PRIMARY KEY` подразумевает `NOT NULL`, и
рядом с ключом его не пишут (`id bigserial constraint user_pk primary key` в
эталоне). Учитываются оба написания — ограничение у колонки и строка
`PRIMARY KEY (id)`; `ALTER TABLE ... ADD CONSTRAINT` не разбирается вовсе, там
у колонок и так стоит явный `NOT NULL`.

**Первичный ключ, получающий значение параметром, помечается предупреждением**
(`fatal=False`, запрос всё равно пишется) — во вставке и в любом
`UPDATE ... SET`, включая мягкое и обратное удаление:
ключ обычно выдаёт база, а значение извне ломает нумерацию так, что падает не
виноватый запрос, а следующий, и рвёт ссылки соседних таблиц. Отбирает колонки
`_key_params`, тексты пишут вызывающие: у вставки и у изменения причина разная.
Молчит, если значение ключа написано руками (`nextval(...)`, подзапрос) или
ключ стоит в `WHERE`: `UpdateById` только так и пишется.

Генерация берёт настройки **из памяти**, а не с диска, — несохранённые правки
тоже попадают в файл.

## Подводные камни

**Кнопки создавать только с `color=None`.** Quasar вешает на цветную кнопку класс
`text-primary` и красит текст через `adoptedStyleSheets`; перебить это из своей
таблицы стилей нельзя даже с `!important` и большей специфичностью. Без
`color=None` текст активной CRUD-кнопки сливается с её фоном.

**Пять кнопок в строке таблицы не помещаются общими отступами.** Ряд
`Create/Read/Update/Delete/Join` шире колонки списка, и последняя кнопка
обрезается, поэтому у кнопок сайдбара свой класс `table-btn` с более тесными
отступами. Проверять шириной: `scrollWidth` ряда не должен превышать его
`clientWidth`.

**Выпадающие списки Quasar не открываются под браузерной автоматизацией** — меню
рендерится в портал, а панель браузера в сессии не отображается. Ветки, которые
зависят от выбора в списке (`many` в Read, `SOFT DELETE` в Delete), проверять
вызовом обработчиков напрямую:

```python
from sgbuddy import app
app.wizard.refresh = lambda *a, **k: None   # вне клиента перерисовывать нечего
app.workspace.tables = ...; app.workspace.settings = {}
app.read_form = app.ReadForm(table=..., annotation="many", ...)
app._submit_read(table)
```

**sqlglot нормализует `DEFAULT`**: `now()` разбирается в узел `CurrentTimestamp` и
печатается как `CURRENT_TIMESTAMP`, `false` — как `FALSE`. Позиции токенов для
восстановления исходного текста непригодны (у `now()` в мете только имя без
скобок, у `Boolean` меты нет). Поэтому `_default_sql` приводит результат к виду
из DDL через явную таблицу подстановки; выражения со строковым литералом не
трогает, иначе `DEFAULT 'Hi'` стало бы `'hi'`.

## Проверка изменений

Эталон — `test_data/tables_model/schema.sql`: 16 таблиц, схема `dc`, есть
`dc."user"` с `bigserial`, кавычками в имени и inline-constraints. Пользователь
принимает работу именно на нём. Лежащий рядом `schema.json` — рабочий артефакт,
его можно затирать и пересоздавать.

Менять интерфейс вслепую не стоит: поднять сервер на свободном порту и проверить
вычисленными стилями и текстом страницы через браузерные инструменты, а не
предполагать, что CSS применился.

### Тесты

`tests/` — по файлу на модуль плюс `test_reference_schema.py` на эталонной
схеме. Настройки в тестах собираются не литеральными словарями, а сборщиками из
`tests/conftest.py`: `col`/`entry`/`crud` для запросов и `link`/`chain`/`jcol`/
`with_joins` для цепочек. Ключи `schema.json` заданы в `settings.py` и только
там — тест, повторяющий их строками, разошёлся бы с программой молча.

Формы проверяются прямым вызовом обработчиков (`app._submit_read` и соседние)
при заглушенной перерисовке — так же, как ниже описано для веток с выпадающими
списками.

## Стиль

Комментарии и docstring-и по-русски, объясняют **почему** так сделано, а не что
делает код. Пользователь ведёт переписывание по шагам и формулирует каждый шаг
сам — делать ровно названное и не проектировать следующие шаги вперёд.
